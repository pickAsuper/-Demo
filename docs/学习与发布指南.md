# 用拾物商店学 Electron、数据库与发布

## 第一课：先区分五个词

| 阶段 | 做什么 | 本项目命令 | 产物 |
|---|---|---|---|
| 开发 | 修改代码并实时预览 | `npm run dev` | 正在运行的开发窗口 |
| 构建 | 检查类型，把 TSX / CSS 转为静态资源 | `npm run build` | `dist/` |
| 打包 | 组合页面、主进程、Electron 运行时 | `npm run dist` | `release/` 安装包 |
| 部署 | 在服务器运行 API 和数据库 | Docker Compose | 可访问的 API 服务 |
| 发布 | 提供版本、说明、签名和下载入口 | GitHub Actions / Releases | 用户可以下载的新版本 |

**构建不等于安装包，安装包不等于服务端部署，上传下载包也不会自动升级用户的软件。** 本项目采用手动下载安装新版本，不包含自动更新器。

## 第二课：工具怎么选

VS Code 不是必需，但初学推荐安装。通过「文件 → 打开文件夹」打开整个 `electronDemo`，再用「终端 → 新建终端」执行命令。不要只双击某个 TSX 文件。

建议工具：

- Node.js 24 LTS：运行 npm、Vite、API 和构建脚本。
- VS Code：写代码、看中文注释和终端输出；可安装中文语言包与 Prettier。
- Git：记录代码版本。项目尚未替你创建远程仓库。
- Docker：学习部署时再安装，不是本地快速启动的前提。
- 数据库客户端：可选，例如 DBeaver、DataGrip 或 VS Code 的 PostgreSQL 扩展。

Windows 编写代码使用 VS Code 没问题。**Windows 的 Visual Studio / Build Tools 与 VS Code 是两个产品**；未来如果引入需要编译的原生模块，可能才需要额外的 C++ 构建工具。

检查环境：

```bash
node --version
npm --version
```

## 第三课：启动、停止和数据保存在哪里

### 路线 A：不安装数据库，最快体验

```bash
npm install
npm run dev
```

开发启动器会启动 PostgreSQL 17（完整数据库进程），执行迁移，然后启动 API、Vite 和 Electron。第一次需要下载依赖；以后通常启动更快。

| 项目 | 位置 / 地址 |
|---|---|
| 商品、库存、订单 | 项目 `.data/postgres/` |
| PostgreSQL | `127.0.0.1:55432` |
| 数据库名 / 用户 | `mono_shop` / `shop` |
| 本地演示密码 | `shop_local_only`（仅本地学习） |
| API 健康检查 | `http://127.0.0.1:3001/api/health` |
| 浏览器预览 | `http://127.0.0.1:5173`（开发服务运行期间） |
| 购物车、设备凭据、连接地址 | Electron `app.getPath('userData')` 所在目录 |

macOS 用户数据通常位于 `~/Library/Application Support/`，开发时一般是 `mono-shop-desktop`，打包后一般是 `Mono Shop`，以 Electron 实际应用名称为准。开发版与安装版可能使用不同的本机数据目录，所以看到的匿名订单列表可能不同。

**按 Ctrl+C 或关闭开发窗口停止。不要强制断电式结束数据库进程。** 异常终止后，先确认没有残留的 PostgreSQL / Node 进程，再重新启动；不要为了消除报错而直接删除数据库目录或锁文件。

重跑种子数据不会重置库存。需要重置时，先停止所有服务，备份 `.data/postgres/`，再移走该目录后启动。这样会创建全新数据库，旧数据不会自动迁移回来。清除 Electron 用户数据会丢失匿名订单访问凭据，数据库里的订单并不会因此删除。

### 路线 B：用 Docker 启动 PostgreSQL

不要同时启动路线 A 的数据库，否则 `55432` 会冲突。

```bash
docker compose up -d db
npm run dev:external-db
```

根目录 `compose.yml` 仅绑定本机数据库端口，使用独立 Docker 卷。它和 `.data/postgres/` 是两个不同数据库。停止容器用 `docker compose down`；日常不要加 `-v`，它会删除数据卷。

### 路线 C：连接已有的 PostgreSQL

先创建数据库，把 `.env.example` 复制为 `.env`，修改连接地址，然后运行：

```bash
npm run dev:external-db
```

`.env` 示例：

```dotenv
DATABASE_URL=postgresql://你的用户:经过URL编码的密码@127.0.0.1:5432/mono_shop
```

普通 `npm run dev` 固定使用项目管理的本地库；只有 `dev:external-db` 才使用自定义数据库。

### 单独启动各部分

想理解进程的区别，可以分别开终端：

```bash
# 终端 1：数据库
npm run db:start

# 终端 2：API，启动时自动迁移
npm run dev:api

# 终端 3：构建页面，再打开 Electron
npm run build
npm start
```

`npm start` 加载已经构建的页面，不负责启动数据库或 API。`npm run dev:web` 只启动 Vite，可在浏览器中预览；浏览器和 Electron 的匿名凭据不同，订单列表也分别独立。

## 第四课：一笔订单怎样走完

1. `src/App.tsx` 收集收货信息与商品 ID、数量，**不把前端价格当作下单依据**。
2. `src/api.ts` 在 Electron 中调用 `window.shopDesktop.request()`。
3. `electron/preload.cjs` 把有限方法暴露给页面；页面没有 `require`，不能任意读硬盘。
4. `electron/main.cjs` 检查发送页面、接口和方法白名单，用 `fetch` 请求 API。
5. `server/app.mjs` 校验输入，从数据库读真实价格，计算运费，执行事务。
6. PostgreSQL 提交成功后返回订单，页面显示成功并清空购物车。

Electron 同时包含 Chromium（页面渲染）和 Node.js（主进程能力）。主进程负责窗口和系统能力，渲染进程负责 React 界面，preload 是受限桥梁。

数据库始终由 API 访问。直接把数据库密码放进 React 或 Electron 安装包，别人解包就能得到它，所以本项目没有这样做。

### 三张业务表

| 表 | 内容 |
|---|---|
| `products` | 商品、价格（分）、可用库存 |
| `orders` | 订单头、匿名设备凭据、收货信息、合计、幂等键 |
| `order_items` | 商品名称 / 价格快照、购买数量 |

另外有 `schema_migrations` 记录已经执行的 SQL 文件。

例如 ¥89 存为整数 `8900`。`orders.total_cents` 必须等于商品金额加运费，库存不能为负数；这些既在代码中检查，也由数据库约束兜底。

### 为什么需要事务、行锁和幂等

事务确保“创建订单”和“扣库存”一起成功，任何一步失败都会 `ROLLBACK`。行锁 `FOR UPDATE` 让同时购买最后一件商品的请求依次检查库存，避免超卖。锁按固定商品 ID 顺序获取，降低死锁概率。

前端每次新的结算内容生成 UUID 幂等键；网络超时后重试保留原键。服务端对同一设备和键加事务锁，已经成功就返回原订单。如果同一键传入了不同商品或地址，则拒绝请求。相关记录暂存于本地存储，成功后清除；只用虚构信息测试。

匿名设备凭据是随机 UUID，作用是隔离教学订单。它相当于本机的访问凭据，**不是正式账号登录**；清除凭据后无法找回订单，知道凭据的人可以使用它。正式产品必须引入用户认证与服务器端授权。

### 用 SQL 亲自观察

连接本地数据库后执行：

```sql
-- 看商品库存和人民币价格。
SELECT id, name, stock, price_cents / 100.0 AS price_yuan
FROM products ORDER BY sort_order;

-- 看最近的订单，不读取收货隐私。
SELECT order_number, total_cents / 100.0 AS total_yuan, created_at
FROM orders ORDER BY created_at DESC LIMIT 10;

-- 理解一对多：一笔订单可以包含多个商品。
SELECT o.order_number, i.product_name, i.quantity, i.price_cents
FROM orders o JOIN order_items i ON i.order_id = o.id;
```

新增表或字段时创建 `002_xxx.sql`，不要修改已经应用到数据库的 `001_initial.sql`。迁移器按文件名排序、逐个执行并记账；备份、回滚方案需要随真实业务的迁移一起设计。

## 第五课：构建——代码变成运行资源

```bash
npm run build
```

依次发生：

1. `tsc --noEmit` 检查前端类型，但不生成 JS 文件。
2. Vite 编译 React TSX、合并与压缩 JS/CSS，复制商品图片到 `dist/`。
3. `scripts/client-config.mjs` 生成公开的 API 地址配置。

主进程和 API 使用 `.cjs` / `.mjs` JavaScript，直接运行，无需额外编译。`base: './'` 让页面在安装包的 `file://` 路径下也能找到资源。

开发页面允许 React 热更新所需的内联脚本；构建页面恢复严格内容安全策略。主窗口还启用了 `contextIsolation`、`sandbox`，关闭了 `nodeIntegration`，并拒绝未知 IPC、弹窗和外部导航。

## 第六课：打包——让别人不用装 Node.js 也能运行

```bash
# 先输出一个应用目录（较快），用于初步验证。
npm run pack

# 再生成当前系统的安装包。
npm run dist
```

输出在 `release/`。macOS Apple Silicon 通常会出现：

```text
release/
  mac-arm64/Mono Shop.app
  Mono Shop-0.1.0-arm64.dmg
  Mono Shop-0.1.0-arm64-mac.zip
```

配置位于 `electron-builder.yml`：

- `appId`：应用身份标识。正式发布后尽量保持稳定。
- `productName`：用户看到的应用名称。
- `files`：只打包 React 构建产物、Electron 文件和元数据。
- `extraResources`：把默认 API 地址放在应用资源目录。
- `mac` / `win` / `linux`：各系统的安装格式与图标。

API、PostgreSQL、`.env`、测试数据库和服务端密码都不会被打包。ASAR 只是归档格式，不是加密。

### 安装包连接哪一个服务器

本地默认是 `http://127.0.0.1:3001`。部署后可以在应用「连接设置」输入 `https://shop.example.com`，或者构建时设置默认值：

macOS / Linux：

```bash
SHOP_API_URL=https://shop.example.com npm run dist
```

Windows PowerShell：

```powershell
$env:SHOP_API_URL = "https://shop.example.com"
npm run dist
```

地址优先级：进程环境变量 > 用户保存的地址 > 打包的默认地址 > 本地默认值。因此用户之前修改过连接设置时，重新安装不会自动覆盖他的设置。

### 在本机体验打包版

1. 关闭 `npm run dev`。
2. 分别启动 `npm run db:start` 与 `npm run dev:api`，保持两个终端运行。
3. 打开 `release/mac-arm64/Mono Shop.app`，或打开 DMG 后拖到「应用程序」。
4. 在连接设置确认是 `http://127.0.0.1:3001`。

macOS 教学包没有配置 Developer ID 签名与公证。系统可能阻止打开未验证的应用；对你自己构建且确认可信的包，可按 macOS「隐私与安全性」提示处理。不要为此全局关闭 Gatekeeper。

### 跨平台不是改个后缀

Windows 包最好在 Windows 构建，macOS 包在 macOS 构建，Linux 包在 Linux 构建。架构也要区分 `arm64` / `x64`。

```bash
npm run dist:mac
npm run dist:win
npm run dist:linux
```

这些命令选择目标系统，但不保证当前电脑具备跨平台构建所需的工具。项目附带 GitHub Actions，在各系统上分别运行 `npm run dist`。工作流每个系统只构建其 runner 的默认架构；有其他架构需求时显式扩充矩阵，并在真实设备上测试。

## 第七课：部署——API 和 PostgreSQL 放到服务器

桌面端交付给用户，API 与数据库放在你控制的服务器上。这里给出可复现的 Docker Compose 教学部署；本次没有替你购买服务器、配置域名或执行公网部署。

### 先在服务器的本机地址跑通

准备一台安装了 Docker Engine 与 Compose 插件的 Linux 服务器，把项目通过 Git 或文件传输放上去，然后在项目根目录：

```bash
cp deploy/.env.example deploy/.env
openssl rand -hex 24
```

把上一步随机字符串填到 `deploy/.env` 的 `POSTGRES_PASSWORD`。不要使用示例密码。使用十六进制避免密码进入连接 URL 时需要额外编码。

```bash
docker compose --env-file deploy/.env -f deploy/compose.yml up -d --build
docker compose --env-file deploy/.env -f deploy/compose.yml ps
curl http://127.0.0.1:3001/api/health
```

预期响应：

```json
{"status":"ok","database":"PostgreSQL"}
```

API 以容器内非 root 用户运行，数据库不暴露宿主机端口。API 启动前等待数据库健康，再自动执行迁移。默认 API 只绑定宿主机回环地址，所以这一步还不能让外部电脑访问。

查看日志：

```bash
docker compose --env-file deploy/.env -f deploy/compose.yml logs --tail=100 api
```

### 用自己的域名启用 HTTPS

1. 将 `shop.example.com` 的 DNS A 记录指向你的服务器。
2. 放行服务器入站 TCP 80、443；不要放行 PostgreSQL 5432。
3. 在 `deploy/.env` 设置实际 `SHOP_DOMAIN` 和 `ACME_EMAIL`。
4. 启用 `public` profile：

```bash
docker compose --env-file deploy/.env -f deploy/compose.yml --profile public up -d --build
curl https://shop.example.com/api/health
```

Caddy 自动申请证书并转发到 API。若证书失败，先检查域名解析、端口和 Caddy 日志。`TRUST_PROXY=1` 只适合当前单层可信 Caddy 代理拓扑，调整代理层级时应同步调整。

本接口为匿名教学演示，仅有基础限流。需要在公网供真实顾客使用时，应先补齐账号认证、服务器端权限、监控、审计与滥用防护；不要把虚构下单流程直接当成正式营业系统。

### 备份和升级

```bash
# 在服务器项目目录执行，保存逻辑备份。
docker compose --env-file deploy/.env -f deploy/compose.yml exec -T db \
  pg_dump -U shop -d mono_shop > mono-shop-backup.sql

# 更新代码后重建 API，数据卷保持不变。
docker compose --env-file deploy/.env -f deploy/compose.yml up -d --build api
```

不要执行 `docker compose down -v` 来“重启”，它会删除数据库卷。备份应定期复制到另一台设备，并定期演练恢复。大版本 PostgreSQL 升级不能只改镜像标签，需要 `pg_upgrade` 或导出 / 导入计划。

修改 `POSTGRES_PASSWORD` 环境变量不会自动修改已经初始化的数据卷里的数据库用户密码；已有数据库应通过 SQL 有计划地轮换密码，再更新 API 配置。

## 第八课：发布——让别人下载正确版本

### 本地手动发布流程

```bash
# 例如从 0.1.0 升级到 0.1.1，不自动创建 Git 标签。
npm version patch --no-git-tag-version
npm test
npm run build
npm run test:desktop
npm run dist
```

把版本变化提交到 Git。使用实际服务器地址重新打包，在目标设备安装测试，再上传到你选择的下载渠道。版本说明至少写清：版本号、平台与架构、功能变化、已知限制，以及是否签名。

### GitHub Actions 生成发布草稿

1. 创建自己的 GitHub 仓库，将项目推送到默认分支。不要提交 `.env`、`.data/`、`node_modules/` 或安装包。
2. 在仓库 Actions 页选择「构建桌面安装包（发布草稿）」。
3. 点击 Run workflow，输入已经部署好的 HTTPS API 根地址。
4. 工作流先运行数据库测试和构建，再在 macOS、Windows、Linux 上各自打包。
5. 成功后汇总安装包与 `SHA256SUMS.txt`，创建 **Draft Release**，不会自动公开发布。
6. 下载各平台包安装验证，补充版本说明后再手动发布。

版本号来自根目录 `package.json`。每次发布先递增版本；不要让新内容复用已经公开的版本号。工作流会绑定本次提交。首次使用请确认仓库允许 Actions 创建 Release；所需写权限仅授予发布草稿的 job。

### 正式分发需要签名

当前配置明确设置 `mac.identity: null`，并在 CI 关闭自动证书发现，方便本机学习。**它不能直接代表正式签名发布流程已经完成。**

macOS 正式分发通常需要 Apple Developer 账号、Developer ID Application 证书、签名与公证：

1. 删除 `electron-builder.yml` 中的 `identity: null`，移除 CI 的 `CSC_IDENTITY_AUTO_DISCOVERY: "false"`。
2. 配置 `mac.hardenedRuntime: true`，为所用 Electron 版本准备正确的 entitlements。
3. 在 CI Secrets 中保存 `CSC_LINK`、`CSC_KEY_PASSWORD`；采用 App Store Connect API key 或 Apple ID 专用密码配置公证。
4. 按 electron-builder 当前文档配置 `notarize`；成功后验证签名、公证状态，并在干净的 Mac 上下载安装测试。

Windows 正式分发需要代码签名证书或受支持的签名服务，并在构建过程中签名 EXE；证书私钥和口令只放 CI Secrets。macOS 与 Windows 的签名凭据用途不同，应分别配置。

参考官方文档：[Electron 打包](https://www.electronjs.org/docs/latest/tutorial/application-distribution)、[electron-builder](https://www.electron.build/)、[electron-builder 代码签名](https://www.electron.build/code-signing.html)。证书与平台要求会变化，购买和配置前以官方当前说明为准。

### 自动更新是后续独立课题

本项目不包含 `electron-updater`。如果未来添加，需要配置更新服务器 / 发布渠道、签名、更新元数据、版本比较、下载进度、失败恢复和更新时机。不要只上传一个 ZIP 就宣称支持自动更新。

## 第九课：遇到问题怎样排查

如果当前网络无法访问 GitHub 的 Electron 下载，可以仅为这一次安装使用镜像（macOS / Linux）：

```bash
ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ npx install-electron --no
```

Windows PowerShell 先设置 `$env:ELECTRON_MIRROR = "https://npmmirror.com/mirrors/electron/"`，再执行 `npx install-electron --no`。Electron 安装器仍使用 npm 包附带的校验和检查运行时文件，不要关闭校验。

打包时若 Electron 下载也超时，可为 `npm run dist` 设置相同的 `ELECTRON_MIRROR`；不要修改系统全局代理或关闭 TLS 校验来绕过问题。

DMG / 签名工具的下载属于另一套工具链。如果打包卡在下载辅助工具，可只对本次命令再加：

```bash
ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ \
ELECTRON_BUILDER_BINARIES_MIRROR=https://npmmirror.com/mirrors/electron-builder-binaries/ \
npm run dist
```

| 现象 | 排查 |
|---|---|
| Electron 或数据库依赖下载失败 | 检查网络 / npm 代理，重新 `npm install`；不要默认关闭 TLS 校验 |
| 提示端口占用 | 先关闭上一套开发窗口 / 终端；不要同时跑本地内嵌库与 Docker 库 |
| 首页显示服务未连接 | 看 API 终端日志；请求 `/api/health`；确认地址正确 |
| `npm start` 没有页面 | 先 `npm run build`，它加载的是 dist，不启动 Vite |
| 安装包看不到原来的订单 | 检查 API 是否相同，开发 / 安装版的设备凭据是否不同 |
| 数据库连接失败 | 确认数据库已启动、密码、端口、数据库名；外部库使用 `dev:external-db` |
| 安装包连接不了服务器 | `127.0.0.1` 表示当前电脑，不是你的云服务器；换成实际 HTTPS 地址 |
| 改了 `.env` 没效果 | 重启读取它的进程；打包默认地址需重新 build，或直接在应用设置里修改 |
| 订单库存不足 | 刷新商品、减少数量；演示下单会真的扣测试库库存 |
| macOS 提示未验证开发者 | 当前是学习用未签名包；正式分发需要签名与公证 |
| 自动化桌面测试打不开窗口 | 它需要图形桌面；Linux CI 可使用 Xvfb，普通无头服务器不能直接跑桌面 UI |

## 建议的学习顺序

先跑通下单，再读 `src/App.tsx` 与 `src/api.ts`；然后读 `electron/preload.cjs` 和 `electron/main.cjs`；接着读 SQL 表结构与 `server/app.mjs` 的事务；最后亲自执行 build、pack、dist，在另一个数据目录体验安装版，然后进行服务器部署练习。

小练习：给商品增加一个 `brand` 字段，并完成新 SQL 迁移、API 返回、TypeScript 类型和界面展示。它能让你体验一次真正的跨层功能修改。
